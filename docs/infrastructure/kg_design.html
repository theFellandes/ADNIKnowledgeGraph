1. LPG vs Knowledge Graph — The Core Distinction

Your current Neo4j implementation is a Labeled Property Graph (LPG). To become a true Knowledge Graph (KG), it needs semantic grounding — meaning that nodes and relationships carry machine-interpretable references to standard ontologies, enabling reasoning and inference.

🔶 Current State: LPG

(:Patient)-[:HAS_DIAGNOSIS]->(:Diagnosis {diagnosis: "AD"})

Relationships are typed strings. "HAS_DIAGNOSIS" is meaningful to humans but not to machines. No formal ontology backing.

🟢 Target State: KG

(:Patient {rdf_type: "ncit:C16960"})-[:HAS_DIAGNOSIS {uri: "ro:RO_0000091"}]->(:Diagnosis {snomed_code: "26929004"})

Every entity and relationship maps to a standard ontology. Machines can reason: "26929004 IS_A neurodegenerative disease."

Key Insight

You don't need to switch to RDF/SPARQL. Neo4j can be a KG by adding ontology properties to existing nodes and relationships. This is the approach used by Spasov et al. (2024) with AD-DPC ontology in Neo4j, and by Romano et al. (2024) with AlzKB's OWL2 ontology mapped to Neo4j.

Design Principle — Simplicity for Master's Level

Time is stored as properties on Visit nodes (visit_date, months_from_baseline) and as delta_months on FOLLOWED_BY edges. No separate temporal nodes. This is enough for causal discovery on baseline-only data and for tracking patient trajectories. The FOLLOWED_BY chain gives you ordering; properties give you intervals.

5. Index & Constraint Strategy

Uniqueness Constraints (Enforce data integrity)

// Primary identity constraints
CREATE CONSTRAINT patient_ptid IF NOT EXISTS FOR (p:Patient) REQUIRE p.ptid IS UNIQUE;
CREATE CONSTRAINT visit_id IF NOT EXISTS FOR (v:Visit) REQUIRE v.visit_id IS UNIQUE;
CREATE CONSTRAINT mri_image_id IF NOT EXISTS FOR (m:MRIScan) REQUIRE m.image_id IS UNIQUE;
CREATE CONSTRAINT pet_image_id IF NOT EXISTS FOR (p:PETScan) REQUIRE p.image_id IS UNIQUE;
CREATE CONSTRAINT brain_region IF NOT EXISTS FOR (b:BrainRegion) REQUIRE (b.name, b.hemisphere) IS UNIQUE;
CREATE CONSTRAINT ontology_uri IF NOT EXISTS FOR (o:OntologyConcept) REQUIRE o.uri IS UNIQUE;

Performance Indexes (For query anchors)

// Lookup indexes — these are the properties you'll filter on most
CREATE INDEX patient_rid IF NOT EXISTS FOR (p:Patient) ON (p.rid);
CREATE INDEX visit_ptid IF NOT EXISTS FOR (v:Visit) ON (v.ptid);
CREATE INDEX visit_viscode IF NOT EXISTS FOR (v:Visit) ON (v.viscode);
CREATE INDEX visit_phase IF NOT EXISTS FOR (v:Visit) ON (v.phase);
CREATE INDEX dx_label IF NOT EXISTS FOR (d:Diagnosis) ON (d.dx_label);
CREATE INDEX dx_snomed IF NOT EXISTS FOR (d:Diagnosis) ON (d.snomed_code);
CREATE INDEX assess_test IF NOT EXISTS FOR (c:CognitiveAssessment) ON (c.test_name);
CREATE INDEX assess_loinc IF NOT EXISTS FOR (c:CognitiveAssessment) ON (c.loinc_code);
CREATE INDEX csf_assay IF NOT EXISTS FOR (c:CSFBiomarker) ON (c.assay);
CREATE INDEX atn_class IF NOT EXISTS FOR (a:ATNProfile) ON (a.atn_class);
CREATE INDEX pet_tracer IF NOT EXISTS FOR (p:PETScan) ON (p.tracer);
CREATE INDEX vol_region IF NOT EXISTS FOR (v:VolumetricMeasure) ON (v.region_name);
CREATE INDEX med_name IF NOT EXISTS FOR (m:Medication) ON (m.compound_name);
CREATE INDEX gene_symbol IF NOT EXISTS FOR (g:GeneticRiskFactor) ON (g.gene_symbol);
CREATE INDEX ontology_code IF NOT EXISTS FOR (o:OntologyConcept) ON (o.code);
CREATE INDEX ontology_source IF NOT EXISTS FOR (o:OntologyConcept) ON (o.source_ontology);

// Full-text search (Elasticsearch alternative for internal Neo4j queries)
CREATE FULLTEXT INDEX search_patients IF NOT EXISTS FOR (p:Patient) ON EACH [p.ptid];
CREATE FULLTEXT INDEX search_concepts IF NOT EXISTS FOR (o:OntologyConcept) ON EACH [o.label, o.definition];
Indexing Rule of Thumb

Index every property you MATCH/WHERE on. In your KG, the most common query pattern is: find a Patient → traverse to their Visits → filter by diagnosis/biomarker. So Patient.ptid, Visit.ptid, Visit.viscode, and Diagnosis.dx_label are the most critical indexes. The OntologyConcept indexes enable fast concept lookup for semantic queries.

6. How the Research Community Solved This

Directly Relevant Prior Work

ProjectAuthorsApproachWhat We Take From It
AD-DPC Ontology + Neo4j KG Spasov et al. (2024) / Lazarova et al. (2023) Built a data-independent AD ontology (AD-DPC), then populated a Neo4j KG with ADNI data mapped to that ontology. Used 16,227 entries from 2,404 participants. ✅ The closest precedent. They proved that Neo4j can serve as a semantic KG without switching to RDF. Their ontology is domain-independent (not tied to ADNI column names), making it extensible. We adopt this principle but at much larger scale (108 tables vs. their ~12).
AlzKB Romano et al. (2024) Largest AD-specific KG: 118,902 entities, 1.3M relationships. Built OWL2 ontology in Protégé, populated via 21 external databases, deployed in Neo4j. ✅ Our integration target. We link our patient-level data to AlzKB's literature-derived knowledge. Their ontology classes and relationship types provide a ready-made vocabulary for our MAPS_TO edges.
ADKG (Yang et al.) Yang et al. (2025) GPT-4 augmented KG from 160K PubMed abstracts. SpERT model for NER. Entity linking to NCBI Gene, ChEBI, DrugBank, HPO, MeSH. ✅ Their entity linking pipeline (simstring + multi-database) is the gold standard for resolving ADNI column names to ontology terms.
Unified Framework (Dobreva et al.) Dobreva et al. (2025) Systematic review of 43 AD KG papers. Proposed "AD-KG 2.0" framework with decision tree for method selection. ✅ Their framework validates our Construct → Discover → Represent methodology. They recommend starting with structured data KGs before adding literature-derived knowledge.
Causal Discovery on ADNI Shen et al. (2020) Tested FCI and FGES algorithms directly on ADNI biomarker data. FCI with expert guidance recovered the canonical A→T→N cascade. FGES achieved 71% precision, 68% recall. ✅ Direct validation that our planned FCI approach works on ADNI data. They found unguided algorithms miss biology — we'll use our KG's ontology constraints as "expert priors."
What's Original About Your Approach

No existing work combines: (1) a full-scale ADNI data graph (108 tables, 407K nodes) with (2) semantic ontology grounding AND (3) causal discovery integration where discovered causal edges become native KG relationships. Spasov et al. had the ontology but limited data; AlzKB has scale but no patient-level data; Shen et al. had causal discovery but no KG. Your thesis unifies all three.

7. Step-by-Step Implementation Plan

Phase 1: Schema Migration (LPG → KG)

1
Add ontology properties to existing nodes (in-place upgrade)

Don't rebuild the graph. Run Cypher SET commands to add snomed_code, loinc_code, uberon_code properties to existing nodes. This transforms your LPG into a KG without data loss.

// Example: Tag all Diagnosis nodes with SNOMED codes
MATCH (d:Diagnosis) WHERE d.diagnosis = 'AD'
SET d.snomed_code = '26929004', d.rdf_type = 'MONDO:0004975';

MATCH (d:Diagnosis) WHERE d.diagnosis = 'MCI'
SET d.snomed_code = '386806002';

MATCH (d:Diagnosis) WHERE d.diagnosis = 'CN'
SET d.snomed_code = '17621005'; // Cognitively Normal
2
Create OntologyConcept nodes (reference layer)

Import a curated set of ontology concepts relevant to AD. These are your "semantic anchor" nodes that everything MAPS_TO.

// Load core SNOMED concepts
MERGE (c:OntologyConcept {uri: 'snomed:26929004'})
SET c.code = '26929004', c.label = "Alzheimer's disease",
    c.source_ontology = 'SNOMED-CT';

// Load LOINC codes for assessments
MERGE (c:OntologyConcept {uri: 'loinc:72106-8'})
SET c.code = '72106-8', c.label = 'MMSE total score',
    c.source_ontology = 'LOINC';

// Build IS_A hierarchy
MATCH (child:OntologyConcept {uri: 'snomed:26929004'})
MATCH (parent:OntologyConcept {uri: 'snomed:52448006'})
MERGE (child)-[:IS_A]->(parent); // AD IS_A Dementia
3
Create MAPS_TO relationships

Connect existing data nodes to their ontology concepts. This is what makes the graph "semantic."

// Connect Diagnosis nodes to SNOMED concepts
MATCH (d:Diagnosis) WHERE d.snomed_code IS NOT NULL
MATCH (c:OntologyConcept {code: d.snomed_code, source_ontology: 'SNOMED-CT'})
MERGE (d)-[:MAPS_TO {mapping_type: 'exact'}]->(c);

// Connect CognitiveAssessment nodes to LOINC
MATCH (a:CognitiveAssessment) WHERE a.loinc_code IS NOT NULL
MATCH (c:OntologyConcept {code: a.loinc_code, source_ontology: 'LOINC'})
MERGE (a)-[:MAPS_TO {mapping_type: 'exact'}]->(c);
4
Create uniqueness constraints and indexes

Apply all constraints from Section 5 before inserting new data.

Phase 2: Causal Discovery Preparation

5
Extract flat feature matrix from KG for causal algorithms

Cypher query to pull baseline-visit data into a tabular format suitable for PC/FCI/GES/DAG-GNN.

// Extract baseline features for causal discovery
MATCH (p:Patient)-[:HAS_VISIT]->(v:Visit {viscode: 'bl'})
OPTIONAL MATCH (v)-[:HAS_DIAGNOSIS]->(d:Diagnosis)
OPTIONAL MATCH (v)-[:YIELDED_ASSESSMENT]->(mmse:CognitiveAssessment {test_name: 'MMSE'})
OPTIONAL MATCH (v)-[:YIELDED_ASSESSMENT]->(cdr:CognitiveAssessment {test_name: 'CDR'})
OPTIONAL MATCH (v)-[:HAS_CSF_BIOMARKER]->(csf:CSFBiomarker)
OPTIONAL MATCH (v)-[:HAS_ATN_PROFILE]->(atn:ATNProfile)
OPTIONAL MATCH (p)-[:HAS_GENETIC_PROFILE]->(gp:GeneticProfile)
RETURN p.ptid, p.education_years, p.sex, p.birth_year,
       d.dx_label, mmse.total_score AS mmse, cdr.total_score AS cdr,
       csf.abeta42, csf.tau, csf.ptau,
       atn.atn_class, gp.apoe_genotype
6
Run causal discovery algorithms (PC, FCI, GES, DAG-GNN)

Use the extracted matrix. FCI is prioritized for handling latent confounders. Compare outputs across algorithms per Shen et al. (2020) methodology.

7
Embed causal edges back into the KG

Discovered causal relationships become native CAUSES edges with metadata.

// Insert causal discovery result
MATCH (src:OntologyConcept {label: 'Amyloid pathology'})
MATCH (tgt:OntologyConcept {label: 'Tau pathology'})
MERGE (src)-[r:CAUSES]->(tgt)
SET r.algorithm = 'FCI', r.p_value = 0.002,
    r.effect_size = 0.45, r.confidence = 'high',
    r.ro_uri = 'ro:RO_0002411',
    r.validated_by_literature = true;

Phase 3: Validation & AlzKB Integration

8
Validate causal edges against AlzKB and literature

Cross-reference discovered edges with AlzKB's existing relationships. If AlzKB says "Gene X → Protein Y → Disease Z" and your data supports it, mark it as literature-validated.

9
Run DoWhy for causal inference

Using the KG-derived causal DAG as input, estimate specific causal effects (e.g., "What is the causal effect of amyloid positivity on MMSE decline?"). Run refutation tests.

10
Document and defend

Write up the Construct → Discover → Represent pipeline. Show the before/after: LPG query vs. KG semantic query vs. causal query.

Figure 2: Incremental data ingestion — MERGE-based upsert pattern ensures idempotent inserts

def ingest_new_data(driver, table_name: str, rows: list[dict]):
    """Generic incremental ingestion function.
    Works for any ADNI table — uses MERGE to avoid duplicates."""
    
    with driver.session() as session:
        for row in rows:
            ptid = row.get('PTID')
            viscode = row.get('VISCODE2') or row.get('VISCODE')
            
            # 1. Ensure Patient exists
            session.run("""
                MERGE (p:Patient {ptid: $ptid})
                ON CREATE SET p.created_at = datetime()
                ON MATCH SET p.updated_at = datetime()
            """, ptid=ptid)
            
            # 2. Ensure Visit exists and chain
            visit_id = f"{ptid}_{viscode}"
            session.run("""
                MATCH (p:Patient {ptid: $ptid})
                MERGE (v:Visit {visit_id: $visit_id})
                ON CREATE SET v.viscode = $viscode,
                              v.ptid = $ptid,
                              v.visit_date = $visit_date,
                              v.phase = $phase
                MERGE (p)-[:HAS_VISIT]->(v)
            """, ptid=ptid, visit_id=visit_id, viscode=viscode,
                 visit_date=row.get('VISDATE'), phase=row.get('PHASE'))
            
            # 3. Create domain-specific observation (varies by table)
            create_observation(session, table_name, visit_id, row)

You don't need to import all 118K AlzKB entities.
